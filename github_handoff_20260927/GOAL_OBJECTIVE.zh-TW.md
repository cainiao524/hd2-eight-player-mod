# 成品驗收條件

必須逐項證明以下結果，才能宣告八人 Mod 完成：

## A. 加入與名單

- 八個獨立帳號能加入同一隊伍。
- 房主與各客戶端對玩家身分及成員名單保持一致。
- 玩家離隊、重新加入及遊戲原有的重連流程，維持正確的索引與資料對應。
- 額外玩家不會因名單容量、欄位覆蓋或索引衝突而取代既有玩家。

## B. 角色建立與控制

- 第 5–8 名玩家各自建立有效角色。
- 所有客戶端能看見並正確識別這些角色。
- 每位玩家能正常操作自己的角色。
- 角色建立、死亡、增援及移除都有完整生命週期。

## C. 任務同步

- 玩家位置、動作、傷害、死亡與增援保持一致。
- 敵人、任務目標、投射物、互動物件及重要任務狀態能同步。
- 不出現額外玩家只能在本機看見、其他客戶端遺漏，或隊伍狀態分裂的情況。

## D. 任務全流程

- 能完成進入任務、降落、遊玩、撤離與結算。
- 玩家離隊及重連後，任務可繼續。
- 遊戲原本支援的房主轉移流程若涉及本次修改，須驗證或明確列為尚未完成的功能。
- 任務結算及相關進度結果經實測確認。

## E. 穩定性與交付

- 八人負載下沒有已知必現的崩潰、越界或資料破壞。
- 明確列出支援的遊戲 build、平台及連線組合。
- 有可重現的建置與安裝方式。
- 有移除、恢復及錯誤診斷說明。
- 有版本不匹配時的檢查與處理。
- 已知限制與未支援情境必須清楚標示。

不得以成功載入 addon、顯示八個槽位、放寬加入比較、靜態測試通過或模擬八份資料，代替上述實測結果。

# 工作順序

## 階段 1：整理最小必要阻礙

建立精簡且持續更新的工作清單，每項包含：

- 要達成的行為。
- 現有證據。
- 尚缺的資訊或實作。
- 下一個具體動作。
- 通過條件。
- 是否依賴使用者、遊戲程序或多人測試。

優先處理會決定整體可行性的未知點：

1. 額外帳號能否通過平台／房間加入流程。
2. 第五名玩家能否建立原生角色。
3. 八份資料是否具備完整儲存與生命週期。
4. 所有客戶端是否能對額外玩家保持一致狀態。

## 階段 2：完成必要布局與原生變更設計

針對以下子系統收束必要修改範圍：

- 房主與客戶端 peer 記錄。
- 原生 roster、entity ID 與 network index 對應。
- 固定四份的玩家元件。
- 角色生成與復活。
- 裝備、玩法更新及玩家相關介面。
- metadata、stack 暫存與逐玩家音效對應。
- 共用節點池與資源所有權。

區分玩家 network index、元件 ordinal、manager ordinal 和其他記錄計數，保留它們原本的映射關係。

對已確認有足夠容量及有效增長機制的元件，保留既有容量機制；任何擴容都要有明確需求依據。

對每份需要搬移或擴大的資料，至少處理：

- 新空間大小與對齊。
- 建立及初始化時機。
- 所有已找到的直接位移、衍生地址與指標副本。
- 加入、更新、移除、壓實及分類轉移。
- 重設、重載、離隊與釋放。
- 失敗或部分配置時的一致性。

## 階段 3：建立候選實作

當一個子系統的必要證據已足夠，就完成對應的候選原始碼與離線驗證。

候選實作應包含：

- 明確的支援版本與目標指紋。
- 可審查的修改位置與理由。
- 初始化、更新及清理的配套。
- 失敗處理與診斷紀錄。
- 有意義的離線檢查。

各子系統完成後，整合為以第五名玩家為首個驗證目標的原型，同時保留最終八人的資料布局與設計需求。

在未取得所需執行授權前，完成可離線完成的實作、建置及審查工作。

## 階段 4：五人驗證

原型與授權具備後，依序驗證：

1. 原有四人行為仍正常。
2. 第五名玩家加入。
3. 第五名玩家建立角色。
4. 所有客戶端看見同一名第五玩家。
5. 移動、戰鬥、互動及任務狀態同步。
6. 死亡、增援、離隊、重連、撤離及結算。

每次測試記錄：

- 遊戲與 Mod 版本。
- 參與帳號／客戶端數量。
- 房主及連線條件。
- 具體操作步驟。
- 預期及實際結果。
- 可供重現的日誌或其他證據。

任何未通過項目都要定位並修正，再繼續相關測試。

## 階段 5：六至八人驗證與封裝

在第五人全流程通過後，逐步驗證六、七、八人。

檢查所有客戶端一致性、任務生命週期、長時間遊玩、資源使用及負載。

完成後交付可安裝版本、原始碼、建置方法、使用說明與測試紀錄。

# 共用節點池的特別要求

容量估算必須涵蓋：

- 最終配置所需節點。
- 尚未回收的舊配置。
- 模板轉換中途的額外占用。
- 其他共用池使用者。
- 部分配置、重入或失敗後留下的狀態。

對「前後各需五格，中途可能需六格」這類已出現的模型線索，完成原始指令及前提核對後，納入配置與失敗處理設計。

不可只依當前count、顯示旗標或最終模板需求判定節點已釋放。

# 研究與驗證原則

每項新增研究都必須回答：

1. 它在解決哪個成品需求？
2. 結果會改變哪個實作決策？
3. 取得什麼證據後可以停止追查？
4. 下一步如何轉成程式變更或執行驗證？

區分：

- 直接觀察到的事實。
- 指令與資料流推導。
- 有前提的模型結果。
- 尚未驗證的假設。
- 多人執行結果。

已充分核對的內容只在版本、依賴或具體風險改變時重新檢查。測試範圍應對應實際風險與驗收條件。

有限掃描結果須保留覆蓋界限；「沒有找到」不能直接等同「不存在」。

新的分析先核對再併入正式結論。尚未重跑或審查的輸出要明確標示。

# 進度管理與阻礙處理

持續朝完整八人目標推進，以以下成果回報進度：

- 關鍵未知得到確認或否定。
- 必要實作完成。
- 可重现的失敗被修正。
- 原型通過具體驗收項目。
- 確認目前確實需要哪項外部條件。

文件及模型應支援實作決策，不以檔案數、分析行數或測試數作為完成程度。

當某項工作依賴尚未提供的授權、執行資料或多人條件時：

- 保存已完成成果。
- 說明具體阻礙及解除條件。
- 完成其他仍可進行的必要工作。
- 在已無有意義的獨立工作時，如實回報受阻並依目標管理規則處理。
- 保持完整八人目標，不將研究報告或較少人數版本改列為最終完成。

如果證據顯示目前方案無法達成必要条件，說明證據、失敗位置及仍可驗證的替代方案，不宣稱不存在的成功結果。
