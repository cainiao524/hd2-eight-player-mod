# 目標

基於 HellForge，突破《Helldivers 2》原版四人限制，建立人數可配置、容量可繼續擴展的多人實作，讓新增玩家完整接入原生 UI、聯網及實際遊玩流程。

先打通第五名真人的完整生命週期與對應原生 UI，再完成八名真人、八個獨立帳號／客戶端的完整任務與界面驗收。八人是首個主要驗收里程碑，不是長期架構的固定上限；之後依證據擴大支持人數。

交付包含可安裝 Mod、原始碼、相容版本、配置與容量限制、安裝／移除方法，以及可核對的多人和原生 UI 實測紀錄。分開記錄配置上限、各子系統實作上限與真實驗證人數；只公布有證據支持的範圍，不承諾無限玩家、任意人數的效能或未驗證的相容性。

2026-10-26 依使用者轉達的主線方向調整；技術缺口及實施規則以 [HellForge 容量與 UI 計畫](../hellforge_multiplayer/CAPACITY_UI_PLAN.zh-CN.md)、[現行交接](../hellforge_multiplayer/HANDOFF.zh-CN.md)與 `hellforge_multiplayer/status.json` 同步追蹤。既有八槽候選與離線證據仍按原範圍有效，不能視為已完成可配置容量。

# 成品驗收條件

以下為八人主要里程碑的必要條件；原生 UI 與容量配置是同一交付標準的必要部分。第五人先以相同類別驗收，八人通過後再按證據擴大範圍：

## A. 加入與名單

- 八個獨立帳號能加入同一隊伍。
- 房主與各客戶端對玩家身分及成員名單保持一致。
- 玩家離隊、重新加入及遊戲原有的重連流程，維持正確的索引與資料對應。
- 額外玩家不會因名單容量、欄位覆蓋或索引衝突而取代既有玩家。

## B. 角色建立與控制

- 第 5–8 名玩家各自建立有效角色。
- 所有客戶端能看見並正確識別這些角色。
- 每位玩家能正常操作自己的角色。
- 角色建立、死亡、增援及移除都有完整生命週期。

## C. 任務同步

- 玩家位置、動作、傷害、死亡與增援保持一致。
- 敵人、任務目標、投射物、互動物件及重要任務狀態能同步。
- 不出現額外玩家只能在本機看見、其他客戶端遺漏，或隊伍狀態分裂的情況。

## D. 任務全流程

- 能完成進入任務、降落、遊玩、撤離與結算。
- 玩家離隊及重連後，任務可繼續。
- 遊戲原本支援的房主轉移流程若涉及本次修改，須驗證或明確列為尚未完成的功能。
- 任務結算及相關進度結果經實測確認。

## E. 穩定性與交付

- 八人負載下沒有已知必現的崩潰、越界或資料破壞。
- 明確列出支援的遊戲 build、平台及連線組合。
- 有可重現的建置與安裝方式。
- 有移除、恢復及錯誤診斷說明。
- 有版本不匹配時的檢查與處理。
- 已知限制與未支援情境必須清楚標示。

## F. 原生玩家 UI

- 任務隊友列表完整顯示每名玩家的名字、血量、狀態及語音。
- 頭頂與地圖標記的身份、編號、顏色一致；移除、重連、死亡與觀戰後不串人。
- 大廳／備戰列表、準備狀態與裝備選擇覆蓋全部玩家。
- 觀戰及玩家操作可選擇全部有效目標，手柄焦點與操作身份一致。
- 任務結算統計與獎勵顯示覆蓋所有參與者，不截斷、重複或錯配。
- 不同解析度、UI 縮放、語言與鍵鼠／手柄有明確驗收記錄。分欄、分組與分頁按容量與 UI 計畫執行，未測組合明列限制。
- 額外繪圖層可以除錯，但不能代替原生 UI 和完整任務流程。

## G. 可配置容量與擴展

- 以統一容量契約連接房間、peer、名冊、角色資源、複製和 UI；版本與各端能力相容後才提交。
- 配置請求上限、每個子系統實作上限、真實驗證人數分欄記錄。未知上限不能視為無上限。
- 逐步消除可替換的固定 4／8／16 假設，保留真正的協定／引擎限制及明確拒絕行為；不得越界接納。
- 已驗證八槽實作可作為階段原型，但不能以替換常量或後端成員數宣稱任意人數已支持。
- 超過當前證據支持範圍的人數，須完成對應實作、UI、效能和完整任務驗收後才公布支持。

不得以成功載入 addon、顯示八個槽位、放寬加入比較、靜態測試通過或模擬八份資料，代替上述實測結果。兩台電腦各一個客戶端僅證明相應雙客戶端範圍，某個 16 項緩衝區亦不構成 16 人實測。

# 工作順序

## 階段 1：整理最小必要阻礙

建立精簡且持續更新的工作清單，每項包含：

- 要達成的行為。
- 現有證據。
- 尚缺的資訊或實作。
- 下一個具體動作。
- 通過條件。
- 是否依賴使用者、遊戲程序或多人測試。

優先處理會決定整體可行性的未知點：

1. 額外帳號能否通過平台／房間加入流程。
2. 第五名玩家能否建立原生角色。
3. 八份資料是否具備完整儲存與生命週期。
4. 所有客戶端是否能對額外玩家保持一致狀態。
5. 第五人能否進入原生 HUD／標記、大廳備戰、觀戰與結算，且操作與身份一致。

## 階段 2：完成必要布局與原生變更設計

針對以下子系統收束必要修改範圍：

- 房主與客戶端 peer 記錄。
- 原生 roster、entity ID 與 network index 對應。
- 固定四份的玩家元件。
- 角色生成與復活。
- 裝備、玩法更新及玩家相關介面。
- metadata、stack 暫存與逐玩家音效對應。
- 共用節點池與資源所有權。

區分玩家 network index、元件 ordinal、manager ordinal 和其他記錄計數，保留它們原本的映射關係。

對已確認有足夠容量及有效增長機制的元件，保留既有容量機制；任何擴容都要有明確需求依據。

對每份需要搬移或擴大的資料，至少處理：

- 新空間大小與對齊。
- 建立及初始化時機。
- 所有已找到的直接位移、衍生地址與指標副本。
- 加入、更新、移除、壓實及分類轉移。
- 重設、重載、離隊與釋放。
- 失敗或部分配置時的一致性。

## 階段 3：建立候選實作

當一個子系統的必要證據已足夠，就完成對應的候選原始碼與離線驗證。

候選實作應包含：

- 明確的支援版本與目標指紋。
- 可審查的修改位置與理由。
- 初始化、更新及清理的配套。
- 失敗處理與診斷紀錄。
- 有意義的離線檢查。

各子系統完成後，整合為以第五名玩家為首個驗證目標的原型，同時保留八人主要里程碑與後續容量可配置、可擴展的設計需求。原生 UI 與角色／聯網鏈一起實作，不等八人底層全部完成才追補界面。

在未取得所需執行授權前，完成可離線完成的實作、建置及審查工作。

## 階段 4：五人驗證

原型與授權具備後，依序驗證：

1. 原有四人行為仍正常。
2. 第五名玩家加入。
3. 第五名玩家建立角色。
4. 所有客戶端看見同一名第五玩家。
5. 移動、戰鬥、互動及任務狀態同步。
6. 死亡、增援、離隊、重連、撤離及結算。
7. 第五人的所有原生玩家 UI，以及所聲明的解析度／縮放／語言／手柄組合。

每次測試記錄：

- 遊戲與 Mod 版本。
- 參與帳號／客戶端數量。
- 房主及連線條件。
- 具體操作步驟。
- 預期及實際結果。
- 可供重現的日誌或其他證據。

任何未通過項目都要定位並修正，再繼續相關測試。

## 階段 5：六至八人驗證與封裝

在第五人全流程通過後，逐步驗證六、七、八人。

檢查所有客戶端一致性、任務生命週期、完整原生 UI、長時間遊玩、資源使用及負載。

完成後交付可安裝版本、原始碼、建置方法、使用說明與測試紀錄。

## 階段 6：依證據擴展

八人主要里程碑完成後，按各子系統上限清單選定下一個具體人數，完成配置、必要布局／協定與 UI 擴展，再驗證完整任務。公布支持範圍必須與版本、設備和測試條件相符，不預先承諾更高人數的效能。

# 共用節點池的特別要求

容量估算必須涵蓋：

- 最終配置所需節點。
- 尚未回收的舊配置。
- 模板轉換中途的額外占用。
- 其他共用池使用者。
- 部分配置、重入或失敗後留下的狀態。

對「前後各需五格，中途可能需六格」這類已出現的模型線索，完成原始指令及前提核對後，納入配置與失敗處理設計。

不可只依當前count、顯示旗標或最終模板需求判定節點已釋放。

# 研究與驗證原則

每項新增研究都必須回答：

1. 它在解決哪個成品需求？
2. 結果會改變哪個實作決策？
3. 取得什麼證據後可以停止追查？
4. 下一步如何轉成程式變更或執行驗證？

區分：

- 直接觀察到的事實。
- 指令與資料流推導。
- 有前提的模型結果。
- 尚未驗證的假設。
- 多人執行結果。

已充分核對的內容只在版本、依賴或具體風險改變時重新檢查。測試範圍應對應實際風險與驗收條件。

有限掃描結果須保留覆蓋界限；「沒有找到」不能直接等同「不存在」。

新的分析先核對再併入正式結論。尚未重跑或審查的輸出要明確標示。

# 進度管理與阻礙處理

持續朝可配置、可擴展且具備原生 UI 的多人目標推進，先完成第五人再完成八人主要里程碑，以以下成果回報進度：

- 關鍵未知得到確認或否定。
- 必要實作完成。
- 可重现的失敗被修正。
- 原型通過具體驗收項目。
- 確認目前確實需要哪項外部條件。

文件及模型應支援實作決策，不以檔案數、分析行數或測試數作為完成程度。

當某項工作依賴尚未提供的授權、執行資料或多人條件時：

- 保存已完成成果。
- 說明具體阻礙及解除條件。
- 完成其他仍可進行的必要工作。
- 在已無有意義的獨立工作時，如實回報受阻並依目標管理規則處理。
- 保持可配置容量、原生 UI 與八人主要里程碑的要求，不將研究報告、額外繪圖層或較少人數版本改列為最終完成。

如果證據顯示目前方案無法達成必要条件，說明證據、失敗位置及仍可驗證的替代方案，不宣稱不存在的成功結果。

使用繁體中文，優先說明：
