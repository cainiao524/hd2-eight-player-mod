# Player index and request layout: bounded offline evidence

This note concerns the captured `game.dll` for Steam build `25480438` only. The reader in `research_handoff_20260927/indirect/inspect_capture.py` revalidated `capture-report.json` SHA-256 `132c49c2189e311f366a3a2f0ed3e67051ca4b30a4543420e49c53632671ffd5` and `captured-data.bin` SHA-256 `31b014a13f219a8e25843c5acb7e4b73db44fccca5c952fbf93d77694e3b625d` before disassembly. The capture identity is `5888cbfe7abe46965b752715414b550a8d09bed968c0c55109a22c30cdbeb4d8`. No game process or installed files were touched. The linked `protocol_*.json` files retain each instruction's bytes, SHA-256, unwind-bounded fragment, and full-fragment hash.

## Confirmed host index allocator

The join handler's root is `0x108BC70`; this block is in its `0x108BE06–0x108C5BE` unwind fragment. A preceding capacity test (`0x108C18F–0x108C1D6`) limits the host to four occupied slots. A separate allocator at `0x108C3B3–0x108C403` operates on four byte flags in the host object:

| RVA | Instruction | Consequence |
| --- | --- | --- |
| `0x108C3D1` | `mov dword ptr [rdx + 0x14], 0xffffffff` | Start with 32-bit unassigned sentinel in the selected member slot. |
| `0x108C3D8` / `0x108C3DB` | `cmp byte ptr [rax], r14b` / `je 0x108C3E9` | Find a free byte flag beginning at host `+0x100`. |
| `0x108C3DD–0x108C3E5` | `inc ecx; inc rax; cmp ecx, 4; jb 0x108C3D8` | Search indices `0–3` only. |
| `0x108C3EE` | `mov byte ptr [rax + r9 + 0x100], 1` | Reserve the selected index. |
| `0x108C3FB` | `mov dword ptr [rdx + 0x14], r8d` | Save the 32-bit index in the member slot. |

The exact `0x108C3B3–0x108C403` captured bytes hash to SHA-256 `42baca00a5721e3dd14c866d8d3746dfde7786f72fbc5525a2ec9bb43445a8d3`. In root `0x108D9F0`, `0x108DDCB` reads `dword ptr [r12 + 0x14]` and logs it using `Adding %llx to game session with player index %u` at `0x108DDD0`. That log path validates the field as a player index, not merely an unrelated four-entry bitmap. See `protocol_index_alloc_0.json` through `_3.json`, plus the prior `join_handler_disasm.json`. The `0x108DDCB–0x108DDE7` bytes hash to SHA-256 `90f8c9283bb3b20aa723f4dd99794acdfe620094a1a633912fcb39fbe49347aa`.

These instructions establish an **in-memory 32-bit player index whose allocated values are 0–3** in this build. The allocator alone does not establish the size of its serialized representation; the confirmed-peer descriptor path below provides separate evidence about the field width. The same `0x108D9F0` path calls through a game-session interface at `0x108DDC7` and `0x108DE09` with a 64-bit player identifier in `rdx`. No player-index argument is visible at those two calls. The interface implementation and writable vtable state were not captured, so the downstream behavior is unverified.

## Join callback and response descriptors

The two validated direct call roots for `0x108BC70` are `0xB93350` and `0xBA8CC0`, both after selecting registry tag `0xEC`. An independent constructor trace, saved in `host_event_registration_disasm.json`, follows `0x134D740` into `0xB2AFB0`: this helper stores the host as a listener in multiple registries (18 stores in the helper), including one using `+0x66F8` for the pointer, `+0x6700` for the tag, and `+0x66F0` for its count. Therefore `0xEC` is best described as a **listener or registered-object tag**, not a proven network event number. The latter callback reads an input count at `[rdx+0x18]` (`0xBA8CF7`) and copies that many qword values into a fixed local record beginning at `[rsp+0x98]` (`0xBA8D30–0xBA8D54`). It then copies 48 local bytes (`0xBA8DD2–0xBA8E0E`) and passes the record to `0x108BC70`. The first root also copies 48 bytes from its input record before the same call (`0xB933C2–0xB93406`). The handler reads the count as a dword (`0x108BEFD`) and walks qword member identifiers from record `+8` (`0x108BF0C`, `0x108BFE2`, `0x108BFE6`).

This is **a count-plus-qword-list callback shape**, not evidence of a four-element wire array. The fixed local record contains room for five qword identifiers after its count/padding. `0xBA8CC0` has no visible bound check before its copy; copying six or more qwords would reach its `[rsp+0xC0]` stack cookie. Its caller/decoder may enforce a bound, but that boundary is not captured or identified. The exact `0xBA8CF7–0xBA8D6B` bytes hash to SHA-256 `6f9c5afcdc92648f1cbcc2ffce451f41946b127025b2d1f66aad7b559bb67421`. See `protocol_request_dispatch_1_prologue.json`, `protocol_request_dispatch_1.json`, and `protocol_request_dispatch_2.json`.

The join-status wrapper `0xBE3CF0` builds three descriptors and calls shared dispatch `0xBDE430` at `0xBE3D6C`: an 8-byte identifier (`type 9, size 8`), a 4-byte status (`type 1, size 4`), and an 8-byte final value (`type 9, size 8`). The hard-coded event hash is `0x3E41A4B8`. At the four-slot failure call `0x108C1C1–0x108C1D1`, this final value receives the zero-extended remaining-capacity count. `0xBDE430` invokes a virtual target from uncaptured writable state. The descriptor widths are static code evidence; actual network bytes, framing, and receiving-side interpretation remain unknown. The `0xBE3D12–0xBE3D71` bytes hash to SHA-256 `68c93f7d2012b3f70e5659decf588c5fb7d271adcd7a07638a2ceb8003eed685`; see `status_helper_disasm.json` and `protocol_status_serializer.json`.

`0x108DFC0` (`ready_for_network_play`) also builds 8-byte identifier descriptors and calls `0xBDE430` for other peers (`0x108E095–0x108E10B`), without a visible serialization of the 32-bit player index in this bounded region. See `protocol_index_alloc_4.json` through `_7.json`.

## Confirmed-peer descriptors and client-side capacity

The host's `0x108C760` path traverses four 0x38-byte member slots at `0x108C8E3–0x108C988`. In that loop, `rdi = slot + 0x20`; `0x108C904` reads the slot's dword at `+0x10`, `0x108C91C` reads its player-index dword at `+0x14`, and `0x108C91F` places that value in the fifth call argument for `0xBE4910` at `0x108C923`. The host migration root `0x1089720` also calls `0xBE4910` at `0x108A08F`. The wrapper `0xBE4910` prepares five descriptors for event hash `0x4804FCF4`: two 8-byte identifiers, two 4-byte integer fields (the fourth is the host player index), and one 4-byte status/boolean field. It then calls generic dispatcher `0xBDE430` at `0xBE49B8`. Thus the player index has a **4-byte serialization descriptor** in this path. This is a field width, not a demonstrated wire frame, byte stream, or array capacity. See `protocol_host_to_client_dispatch.json` and `protocol_confirmed_peer_sender.json`.

A matching five-field receiver wrapper `0xBABA80` loads field pointers from offsets `+8,+0x18,+0x28,+0x38,+0x48`; its fourth value becomes the fifth argument to `0xB90B20` at `0xBABAAF`. In `0xB90B20`, the client peer record begins at `client+0xD0`, the count is `dword [client+0xC8]`, and records have 0x20-byte stride (`0xB90BE3–0xB90C03`). At `0xB90C0B–0xB90C12`, the fourth received dword is stored at record `+0x14`. `0x10872C0` has an analogous direct client append at `0x1087333–0x108737B`, but the static xref scan did not find its caller. The wrapper and sender have matching five-field shapes; the capture does not independently resolve the runtime registration binding event hash `0x4804FCF4` to wrapper `0xBABA80`. See `protocol_client_dispatch_alt.json`, `protocol_b90b20_body.json`, and `protocol_client_10872c0_disasm.json`.

The client peer record storage has a **four-record in-object layout**. A distinct client constructor `0x1082F30` initializes count `+0xC8` and an adjacent field at `+0x150`; the owner constructor `0x134D740` uses `owner+0x162C8` as that client object and also initializes `client+0x150,+0x160,+0x170,+0x180` (`0x134DD07–0x134DD81`). The client reset `0x10845B0` clears exactly 128 bytes at `client+0xD0..+0x14F` using eight 16-byte stores (`0x10849F7–0x1084A28`), i.e. four 0x20-byte records. Another client method `0x1084F50` treats `+0x150` as the start of a separate four-entry, 0x10-byte-stride structure (`0x1084F59–0x1084F86`). A fifth append using the current `count << 5` addressing would begin at `client+0x150`, overlapping that distinct structure. Neither `0xB90B20` nor `0x10872C0` shows a count-bounds check before incrementing `+0xC8`, nor a `<4`/`&3` normalization of the received player index after storing it. The legitimate host path currently sends at most four records, but lifting only the host's four-slot admission would leave this client layout unsound. See `protocol_client_ctor_alt.json`, `protocol_client_ctor_layout.json`, `protocol_client_reset_layout.json`, and `protocol_client_adjacent_1084f50.json`.

The client removal method `0x1087540` traverses the same `+0xD0` records by count and 0x20-byte stride, then replaces a removed record with a full 0x20-byte copy of the final record (`0x10875D0–0x108763E`). Reset (`0x10845B0`) also walks these records by count. These consumers establish the record stride and lifecycle but do not independently consume the player-index field at record `+0x14`. See `protocol_client_remove_peer_1.json`, `_2.json`, `_3.json`, and `protocol_client_reset_layout.json`.

## What would distinguish the remaining possibilities

Locate the invoker or decoder that calls `0xBA8CC0`, then verify the declared list bound and how it handles a request with more than four identifiers. Resolve event-hash-to-callback registration and the generic dispatcher's actual encoding. Map other client and gameplay structures whose size or behavior depends on four players. A read-only code capture identifies concrete static constraints; an actual fifth participant appearing and moving in one mission would still require a later authorized live test with five accounts.
