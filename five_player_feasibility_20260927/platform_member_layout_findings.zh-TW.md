# 平台成員列舉緩衝區：第五筆覆蓋控制欄位

本頁使用既有 build `25480438` 的固定捕捉，未再次讀取遊戲程序。[重播器](platform_member_layout_replay.py)先核對兩個來源檔 SHA-256，再按 unwind fragment 驗證 87 個不同指令位置；逐條原始 bytes、雜湊與 root 見[證據 JSON](platform_member_layout_evidence.json)。

## 已確認的布局衝突

既有列舉分析已確認 `0x1092e60` 和 `0x10937a0` 使用四人容量。這次進一步證明，將容量提高而保留現有布局，會覆蓋正在使用的控制資料：

| 欄位 | 相對平台物件偏移 | 保存程式的用途 |
|---|---|---|
| 成員 ID 陣列 | `+0x1b58`，每筆 8 bytes | `0x1092f0a`、`0x1093cfe` 按索引寫入；現有四筆結尾為 `+0x1b78`。 |
| 狀態結果 | `+0x1b78`，4 bytes | 建立路徑初始化為 `0xffffffff`；列舉後 helper 的非負返回值及更新路徑的布林結果會寫到此處。尚未給它確切業務名稱。 |
| 計數／重試控制欄位 | `+0x1b7c`，4 bytes | 建立時清零，更新路徑 `0x1093c49` 遞增；完整業務語義尚未確認。 |
| 浮點控制欄位 | `+0x1b80`，4 bytes | 建立時設為 `0x41200000`（10.0），更新時由 `movss` 讀寫。 |
| 成員計數 | `+0x1bb0`，4 bytes | 列舉完成後保存 count，供後續迴圈使用。 |

若原陣列直接容納第五筆，該 8-byte 寫入覆蓋 `+0x1b78..+0x1b7f`，同時破壞上表兩個控制欄位；八筆的結尾則變成 `+0x1b98`，還跨入其他既有欄位。這是根據已驗證的位址算式得出的衝突，沒有執行越界寫入。

因此，`4` 的列舉參數與回傳人數截斷都需要與成員陣列的儲存變更一起處理。只把截斷值改為 `8` 不構成可用實作。

## 列舉後的讀取端

`0x1093590` 從入口 `RCX` 保留平台物件於 `R14`，讀 `+0x1bb0` count，從 `+0x1b58` 起每次前進 8 bytes。它逐一讀成員 ID、與本機 ID 比較，並以 API `+0xf8/+0x118` 查詢成員相關資料。返回值在列舉 helper 中經非負檢查後寫入 `+0x1b78`。

更新函式 `0x10937a0` 另有兩段同一陣列的 count-driven 讀取：`0x1093da8..0x1093e26` 及 `0x1094381..0x109443b`。後者在 `0x10943a4` 讀 `+0x1b58+8*i`，再查詢成員資料。這些讀取端的迴圈界限來自 count，但使用原陣列位置；搬移陣列時仍需更新它們。此結果沒有涵蓋所有間接使用者。

## 與外層物件的關係

主更新 `0x134e400` 在 `0x134e443` 將 `owner+0x1d470` 傳給 `0x10937a0`。初始化 root `0x134d740` 從 global `0x347cef0` 取得 owner，直接把 `owner+0x1efe8` 設為 `0xffffffff`；`0x1d470 + 0x1b78 = 0x1efe8`，與上述緊鄰陣列的結果欄位相符。這證明不能只更新平台 helper 內部偏移而忽略外層直接初始化。

同一主更新也把 `owner+0x171c8` 傳給 `0x108f040`；後者再把自身 `+0x1c00` 傳給同一平台更新函式。這條路徑的派生位置是 `owner+0x18dc8`。因此已確認至少兩個不同內嵌位置使用相同平台物件布局；名稱、生命週期及其他实例仍須逐一核對，不能假設改一份物件即可。

## 掃描範圍與下一步

[位移掃描](platform_layout_field_scan.json)在限定 code 範圍內找出 38 個帶引用的位移、726 項候選，其中含 stack 及其他物件。只有上述經入口參數、外層呼叫與欄位資料流核對的 87 個指令列為本頁證據；726 項不能當作同一物件的完整修改清單。

此結果新增一組需要擴容的原生儲存區，並指出已確認的寫入端、讀取端和外層直接初始化。它未證明平台服務會接受第五人，也未完成角色生成或八人同場驗證。
