# Client 八槽布局：已確認存取點

範圍是既有 Steam build `25480438` 的 `game.dll` 擷取；`client_expansion_inventory_v2.json` 以原擷取的 SHA-256 重新驗證每個指令邊界及位元組。只做離線讀取，未讀取新的遊戲行程或變更安裝檔。以下「容量」指物件內、下個已用欄位之前可容納的項目數，不代表網路服務容量。

## 物件內相鄰布局

Owner 建構流程於 `0x134DD07` 設 `r8 = owner+0x162C8`，並在此 client 物件設定 `+0xC8` 筆數為零、`+0x150` 為另一個已用欄位 (`0x134DD41`,`0x134DD65`)；獨立建構函式 `0x1082F30` 重複初始化。`0x1087540` 移除流程給出相鄰清單的筆數、起點和步幅：

| 筆數欄位 | 項目起點 | 步幅 | 下一個已用欄位 | 物件內容納 |
| --- | --- | ---: | --- | ---: |
| `+0x10` | `+0x18` | 8 | `+0x38` | 4 |
| `+0x38` | `+0x40` | 16 | `+0x80` | 4 |
| `+0x80` | `+0x88` | 16 | `+0xC8` | 4 |
| `+0xC8` | `+0xD0` | 32 | `+0x150` | 4 |

`+0xD0` 是 confirmed-peer 紀錄，紀錄 `+0x14` 是 32 位元玩家索引。`0x1084F50` 另從物件 `+0x150` 搜尋四個、步幅 16 的 peer-ID keyed 項目 (`0x1084F59–0x1084F95`)；其 caller `0x1084ED0` 原樣傳遞 `RCX`，與 owner 建構的 client 指標之間沒有在此證據中完整閉合，因此單獨視為**相同布局的候選鄰區使用者**。即使不依賴此函式，建構函式對 `client+0x150` 的寫入已證明第五個 `+0xD0` 紀錄會與既有欄位重疊。

## 依筆數運作的流程與固定四筆的流程

- 新增：註冊 tag `0xEB` 的 callback root `0xB90B20` 把 `+0xC8` 左移 5 位算 0x20 步幅，在 `0xB90C03` 遞增筆數，`0xB90C12` 寫 record `+0x14`。直接方法 `0x10872C0` 同樣做法 (`0x1087333–0x108736A`)，但靜態掃描沒有找到它的直接 caller。兩者都未在新增前顯示 `<4` 檢查；只改主機加入上限會使第五筆從 `client+0x150` 開始寫。若另有真正八筆儲存空間，這些 count/stride 算式本身可處理較高筆數，仍需確認上游給定上限。
- 移除與重排：`0x1087540` 先按 `+0xC8` 與 0x20 步幅尋找 peer ID，減少筆數，再以兩次 16 位元組複製，把最後一筆完整紀錄搬入空位 (`0x10875D0–0x108763E`)。這套算式跟著筆數走；同函式另處理表中前三個相鄰清單，其中 `+0x88` 清單還有固定四項的 ID 搜尋 (`0x108771C–0x1087733`)。
- 重設：`0x10845B0` 與 `0x1087010` 都先按 `+0xC8` 筆數逐筆處理，之後將筆數歸零，但各自只用八次 16 位元組 store 清除 `+0xD0..+0x14F`，即固定 **0x80 位元組／四筆** (`0x10849F7–0x1084A28`; `0x1087260–0x1087298`)。八筆布局需要相應擴充清除範圍並避免觸及相鄰結構。
- 踢出／主機遷移連結：`0xB91320` 對 tag `0xEB` client 指標按 `+0xC8` 走訪，呼叫 `0x1087540` 移除同伴 (`0xB9140A–0xB9144F`)，隨後於 `0xB9159D` 呼叫獨立的 host migration root `0x1089720`。後者仍使用四個主機 slot，並將遷移來的索引寫入 host slot `+0x14`；這不是 client peer record `+0x14` 的讀取。

## 索引讀者的證據界線

既有的 34 個 `ClientSynchronizer` 字串候選 root 中，record `+0x14` 的已證實 scalar 操作只有 `0xB90C12` 與 `0x108736A` 兩個寫入。其餘兩個 `+0x14` 候選是 `0x1083F4F` 對另一個全域整數列表取位址，以及 `0x10851EF` 對 tag `0xB5` 註冊物件寫入一個 byte，均不是 record index 讀者。針對相鄰 client 代碼區 `0x1080000–0x1092000`、`0xB90000–0xB93000` 的補充掃描，未找到以固定 `+0xE4,+0x104,+0x124,+0x144` 位移讀取四筆 record 的指令。此結果**不能排除**其他函式用已計算的 record 指標讀 `+0x14`，或透過整筆複製帶出該欄位。

看到的其他 `+0x14` 讀取必須按 base 區分：`0x1087945` 與 `0xB919C4` 是另一個事件物件的清單筆數；`0x108BB76` 與 `0x108DDCB` 是 **host** member slot 的玩家索引。它們均不能當成 client record 索引的已知讀者。`client_expansion_inventory_v2.json` 保存這些排除例的指令位元組和 root。

以上只列明目前可證實的擴容接點。連續內嵌清單與 `+0x150` 鄰區意味著八槽需要整體重新安排 client 物件布局，並檢查所有後續欄位的引用；尚無證據可證實第五位玩家會完成網路加入、生成或任務同步。
