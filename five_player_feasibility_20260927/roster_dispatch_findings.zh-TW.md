# Roster 插入入口與 tag 0x69 分派：離線核實

本輪只讀既有 build `25480438` 固定擷取，未讀遊戲程序。重播工具為 [`roster_dispatch_replay.py`](roster_dispatch_replay.py)，本輪正式輸出為 [`roster_dispatch_evidence_v2.json`](roster_dispatch_evidence_v2.json)。原始擷取指紋由 `Image` 固定檢查；`runtime_verified=false`。

## 插入與移除入口沒有冷段誤判

六個入口都恰為各自 `RUNTIME_FUNCTION` 的起點，unwind chain 沒有連回另一個 root。其實作前有函式結束及 `CC` padding，實作本身有完整 prologue/epilogue。因此可以把它們列為六個獨立的靜態實作；仍不能推論其執行期可達性。

| 入口 | 捕捉 unwind 範圍（終點不含） | 從入口參數讀取的來源 |
| --- | --- | --- |
| `0x540850` | `0x540850..0x54091E` | 物件指標 `RCX` |
| `0x540920` | `0x540920..0x540A3E` | 物件指標 `RCX`；旗標指標 `RDX` |
| `0x540A40` | `0x540A40..0x540AE0` | 由 `RCX+8` 讀物件識別值 |
| `0x60CA80` | `0x60CA80..0x60CB9F` | 物件指標 `RDX`；旗標指標 `R8` |
| `0x60CBA0` | `0x60CBA0..0x60CC6B` | 物件指標 `RDX` |
| `0x60CEA0` | `0x60CEA0..0x60CF4C` | 由 `RDX+8` 讀識別值、`RDX+0x10` 讀返回值 |

前後兩組的參數位置不同，不能共用同一個未經參數轉換的 detour。入口參數位置本身不能證明它們是哪一種 callback 或 C++ 方法。

新增掃描直接在整段已捕捉 code 的原始位元組搜尋 `E8/E9 rel32` 及 `0F80..0F8F rel32`，目標覆蓋六個函式的**整個範圍**，沒有任何候選。這項結果不依賴 caller 的 unwind 記錄，因此排除了「既有掃描只是漏掉無 unwind 的直接 caller」這個解釋，限於上述指令形式。附近短跳形式 `EB/70..7F/E3` 有四個原始候選，均沒有已驗證的來源邊界，其中三個目的位於已驗證指令內部。第四個 `0x60CE83→0x60CECD` 的目的確為有效指令；來源在未涵蓋 unwind 的鄰近 leaf 區域，看似 `0x60CE80 mov r9d,[rcx+0x7C]` 的位移 byte，但沒有把該 leaf 入口當作已證實，故保留為未驗證原始候選。這些候選均未建立新的正常控制流入口。間接指標、計算位址、動態資料及未捕捉區域仍未解決。

## tag 0x69 確實被消費，但沒有找到插入 callback

註冊函式 `0xB27560` 的 registry 全域為 `0x3326E68`。註冊值是 `{roster pointer, tag 0x69}`，每筆 16 bytes。這次沿相同 registry 的各個陣列，找到明確比較 `0x69` 後直接使用 roster 的邏輯：

| registry 陣列起點／計數 | 消費根入口 | 已驗證的 roster 使用 |
| --- | --- | --- |
| `+0x5420 / +0x5418` | `0xB833F0` | `0xB8342C` 檢查 tag，`0xB8344C` 取物件；依 `+0x84` 計數迴圈寫 `+0x2D8 + ordinal*0x38 = 1`。 |
| `+0x5438 / +0x5430` | `0xB83510` | `0xB83557` 檢查 tag，`0xB83562` 取物件；迴圈讀 `+0xE8 + ordinal*8`，匹配後寫同一組 `0x38` 記錄中的 `+0x2D8` 欄位。 |
| `+0x5450 / +0x5448` | `0xB83600` | `0xB8364B/57` 比對 tag 並取物件；讀 `+0x88`、第一個 `+0xE8` 指標及 hash ordinal，再讀 `+0x108 + ordinal*0x70`。 |
| `+0x5468 / +0x5460` | `0xB83750` | `0xB83785/8F` 比對 tag 並取物件；當 `+0x88 >= 1`，寫第一組記錄 `+0x140 = 9`。 |
| `+0x5480 / +0x5478` | `0xB83820` | `0xB8387D/8F` 比對 tag 並取物件；hash 取得 ordinal，寫 `+0x2D4 + ordinal*0x38`，另讀 `+0xE8` 指標。 |
| `+0x5498 / +0x5490` | `0xB83AD0` | `0xB83B05/16` 比對 tag 並取物件；hash 命中後以此物件作 RCX 呼叫 `0x608B60`。 |
| `+0x10F8 / +0x10F0` | `0xB54E00` | `0xB54E58/5B` 的 tag 0x69 分支至 `0xB55003`；依 `+0x84` 迴圈讀 `+0x3A8`、stride `0x20`，匹配後讀指標陣列並修改 `+0x3AC + ordinal*0x20`。 |

這是正向的「物件註冊 → tag 判斷 → 實際陣列消費」證據。它說明若採外置 roster 儲存，僅改 `0x3326468` 全域並不足夠：registry 中保存的 roster 指標也會被直接解參考，四組固定偏移的讀寫必須一起處理。上述幾條以 `+0x84` 作為迴圈計數，沒有把它们的遍歷上限誤當作固定四；但其陣列基址仍是原四槽布局。

本輪追到的是 roster 的玩法／狀態消費者，尚未把四條插入入口接到實際加入事件。沒有把 tag 0x69 當成插入 callback ID，也沒有證明相關 RPC 或事件的語義名稱。

## 新增限定寫入盤點及下一個缺口

對既有 `0x3326468` 引用中的 950 個 unwind fragment，從每次載入 roster 的原寄存器向後檢查最多 179 條指令，直到顯式改寫該寄存器，列出 `+0x80/+0x84/+0x88/+0xE8` 的 22 個寫入點。結果只有原四個插入、兩個移除，以及 `0x60CF50/0x60D300` 的 `+0x88` 維護。**這不是完整 writer 清單**：没有追蹤跨 fragment 的寄存器別名、registry 取出的物件基底、callee 副作用或每條分支的可達性，不能據此斷言無其他內聯插入。

下一步應以新確認的 registry 分派模型查找物件建立／移除事件的 consumer，並追蹤跨 chained fragment 的資料流；單純重複精確入口 xref 掃描不會補齊這個缺口。現有證據仍不足以縮成一組可安全套用的插入 hook，也不能宣稱八人原生擴容已完成。
