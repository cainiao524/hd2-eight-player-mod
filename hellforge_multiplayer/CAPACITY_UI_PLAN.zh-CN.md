# 可配置多人容量与原生 UI 实施计划

2026-10-26。按用户转达的主线调整更新；本计划规定交付范围，不表示下列功能已经实现。当前固定平台为 HellForge 0.2.0-beta / SDK 13 / build 25480438。

## 目标与公布规则

突破原版四人限制，建立人数可配置、容量可继续扩展的多人实现，让新增玩家接入原生 UI、联网和完整角色/任务生命周期。先打通第五名真实玩家，再完成八个独立账号/客户端的完整任务与界面验收；八人是首个主要验收里程碑，之后按证据扩大支持范围。

分别公布配置请求上限、每个子系统已实现的上限、真实验证人数及测试条件。不承诺无限玩家、任意人数下的性能或未经验证的兼容性。某个缓冲区、模拟节点或菜单可容纳的数量，不等于真实可玩人数。两台电脑各一个客户端只证明对应的双客户端场景。

## 当前容量与缺口

| 子系统 | 当前可核对范围 | 缺口与拒绝规则 |
|---|---|---|
| HellForge 接入层 | `ep_hellforge.h` 请求 8、应用 0，provider 未绑定 | 尚无统一的运行配置和完整事务；不可因请求值为 8 就开放第五人 |
| 名册及元件33候选 | 当前生成器、布局、map 和测试以 8 槽为界 | 仅离线验证，完整生产生命周期未接入；超过当前布局必须拒绝，不能直接增大常量 |
| Loader 读取接口 | `ep_roster_api.h` / 引擎补丁的缓冲区为 16 项 | 16 是接口存储限制；不证明原生存储、协议、角色或 UI 支持 16 人 |
| 原生四槽消费者 | 已确认相邻数组重叠，仍有创建/计分/customization 等四槽约束 | 逐一迁移全部读写与生命周期；未覆盖的消费者阻止容量提交 |
| 后端 | 保存测试执行了 8 个合成端点及第九项拒绝 | 更高人数、Steam 传输、真实接纳和客户端复制均未验证 |
| 协议、peer、资源与任务 | 有保存代码及分派分析 | 上限未闭合，未知不能当作无上限；受限路径需明确拒绝与补偿 |
| 原生玩家 UI | 尚无第五人实现或实机验收 | 在相应 UI 容量完成前不能宣布该人数全流程支持 |
| 真实验证 | 当前 HellForge 多人候选验证人数 0 | 原官方环境四人基线与离线八节点各自保留，不能并入新候选实测人数 |

后续统一配置必须先核对所选 build、所有必需子系统及客户端协商能力，再提交人数变更。可启用人数不得超过其中任何已实现上限；版本、能力或身份不一致时拒绝接纳，不发生越界写入、身份替换或只显示四人的降级。有效支持范围还须受真实验证与 UI 验收约束。

固定 4/8/16 的清理按语义进行：区分玩家容量、map 桶数、指针大小、记录字节数、协议字段与非玩家资源数量。可替换的容量从同一配置契约派生；协议/引擎的真实限制保留明确上限及拒绝行为。原型阶段八槽布局可以继续用，但不能宣称已参数化所有子系统。

## 原生 UI 验收矩阵

以下各项当前均为 **未实现/未实机验证**；具体原生控件、数据绑定和清理路径须先从已有源码与保存证据定位。额外绘图层可辅助调试，不能代替本表验收。

| 界面 | 必须表现的行为 | 首个具体动作 / 通过条件 |
|---|---|---|
| 任务队友列表 | 第五人及其后每人的名字、血量、状态、语音；离队/重连不串人 | 找到原生列表模型、创建/更新/销毁和固定四项约束；房主与所有客户端逐人核对 |
| 头顶及地图标记 | 身份、编号、颜色与权威成员映射一致，死亡/观战/重连后不复用成别人 | 接到稳定成员身份和代次，不用压实后 ordinal 作永久玩家编号；逐客户端对照 |
| 大厅与备战 | 全部成员、准备状态、装备选择及错误提示 | 从已有 MenuScreenLoadout 证据继续核对模型、读写者和切换/析构；完整进出与重连无残留 |
| 观战与玩家操作 | 能选择所有有效玩家，焦点与可执行操作指向正确身份 | 定位目标集合、焦点导航和操作权限校验；第五人可选且移除后焦点安全转移 |
| 结算、统计与奖励 | 所有参与者有对应记录，不截断、不串人、不重复派发 | 连接权威结果数据与原生显示/奖励流程；撤离、离队与重连记录逐人核对 |
| 布局与输入 | 分辨率、缩放、语言、键鼠/手柄均可读可操作 | 使用下述规则与矩阵，记录真实支持组合；未测组合不宣称兼容 |

具体接线需同时覆盖 `14A17E0` 的四个 widget 建构、`1467330`/`1467720` 两条释放及 `1470A40` transition，保留 `1EE18` widget 步幅和不同 nested member 偏移；`189D050` 的 index<4 guard 与 `146E0A0` 更新路径仍需迁移。旧 Python sidecar 模型只有 token/代次和映射，不调用原生 widget。下一 UI 实作应连接这些原生生命周期与数据模型，不能把重跑 sidecar 模型作为 UI 已完成。

## 布局规则（实现规格，尚未验收）

1. 原生模型使用稳定成员身份；显示顺序、UI 位置、网络索引和存储 ordinal 分开。加入时追加，离队或重连时按身份更新；焦点不随存储压实跳到另一玩家。
2. 任务队友列表以每组最多四人为单位。五至八人优先两组并排；可用宽度不足则在安全区内纵向排列。先保留血量、关键状态和语音，再对过长昵称省略；完整昵称在原生详情中可访问。字号下限和最小行距由实机 UI 缩放验收确定，不能靠无限缩小塞入人数。
3. 大厅、备战、观战和结算的可操作列表每页最多八项，页内每组最多四项。跨组/跨页导航有明确方向和页码，返回后恢复同一身份的焦点；本机、选中项和更新提示始终可定位。尚未支持超过八人的构建不能因分页存在而接受第九人。
4. 头顶和地图标记按稳定身份分配编号/颜色，颜色不足时同时用编号/形状区分，离队代次避免错认。拥挤时按原生缩放/遮挡规则处理，需验证重叠与目标选择，不能只显示前四人。
5. HUD 关键状态和标记不能因列表分页而悄悄消失。若指定人数在某个分辨率/缩放组合无法达到可读与可操作标准，该组合的 UI 支持上限应降低或拒绝启用，直到布局修复并验证。

首轮矩阵包含 1280×720、1920×1080、2560×1440、3840×2160、3440×1440；可用的最小/默认/最大 UI 缩放；简中、繁中、英文及长文本语言；键鼠和手柄。实际游戏支持的选项须在获准验证时确认，当前列表只是计划。每项记录人数、分辨率、缩放、语言、输入设备、预期/实际结果与证据。

## 近期实现顺序与停止条件

1. **闭合第五人的存储与 owner 路径。** 收束元件33无损 pending 转换；`576CF0` 内联窗口已有生成/选定路径执行验证；继续接入创建后的 `ADDD85`/`B62400` 等必需读写者，处理旧数据迁移、失败补偿和全调用写入排除。已有同类验证通过后，不以重复增加场景数代替生产连接。
2. **打通真实接纳与角色创建。** 沿 `1086460 → FDC140 → 581320/581780` 接入名册、资源、控制与复制；补齐创建前的统一容量预检和失败后补偿。产出可审查的第五人原型及明确缺口。
3. **同步实现第五人原生 UI。** 任务列表/身份标记与创建链一起绑定；同时覆盖大厅备战、观战、结算和输入布局。接口以稳定身份与配置契约连接，不能等八人底层完成才追补 UI。
4. **准备并申请限定运行验证。** 先交付具体候选、版本/指纹、安装与移除步骤、观察项、读取地址来源/字节预算和停止条件；得到明确授权后才执行。单人/双客户端检查只验证基础条件，然后五名独立玩家完成角色、UI、任务全流程。
5. **八人主要验收与后续扩展。** 五人通过后逐步验证六、七、八人，记录同一版本的完整任务、全部 UI、资源与性能。再依据容量清单消除可替换的固定假设，以新的明确人数和测试条件扩大范围。
