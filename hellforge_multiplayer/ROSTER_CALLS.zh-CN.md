# 十六入口的受管调用与 ABI 桥接

2026-10-26，固定 HellForge SDK 13 / 游戏 build 25480438。`ep_roster_call.*` 将十六入口的整次旧路径或新路径调用接入 `ep_roster_owner.*`。这是显式选择的离线集成接口；Mod 初始化未调用，未在游戏发布。完整目标仍是八个独立账号完成同一任务。

## 路由与参数

使用 `ep_roster_group_prepare_owned(api, mod, bindings, owner_handle, policy, out)`。准备时检查 owner 的 game/S/B 与组完全一致；每次执行还会在锁内再次核对。32-byte 入口用 R10/R11 转交固定 context 和静态桥接地址，不增加动态映像长度，也不改变主体的 base+32 地址。

第 16 个实体删除入口在两种模式下都调用当前 SDK 下一跳，候选主体不会替换原 dispatcher；它把两个回调阶段及其中间空隙包进同一 owner。

调用顺序是：保存参数 → 取得 owner → 读取当前共同开关与下一跳 → 调用目标 → 保存返回寄存器 → 释放 owner → 恢复返回状态。选择路径发生在取得保护以后；排队的入口不会带着已经过期的旧路径选择在切换完成后继续执行。旧路径同样受保护，发布期间仍使用 SDK 提供的下一跳。下一跳为空时隔离该 owner，调用显式失败策略，不跳到未知地址。

发送入口在保存证据中直接读取原 entry RSP+0x28 的 count 指针和 +0x30 的 allocator box 指针。桥接把这两个完整 64-bit 参数复制到新调用帧；其余十五个原函数体未发现明确的额外传参读取，桥接目前不复制额外参数；第 16 个 dispatcher 的回调结果决定局部缓冲区遍历次数，其动态范围尚未证明；离队间接尾调用的真实目标契约尚未证明，不能由此断言完整调用链只需四参数。RCX/RDX/R8/R9、传入 RAX 和 XMM0–5 被转交；正常返回时保存完整 RAX、RCX/RDX/R8/R9/R10/R11 及 XMM0–5。非易失 GPR/XMM 按 Windows x64 ABI 保留。**不承诺保留 RFLAGS，也不把传入 R10/R11 视为已证明的私有参数。**

`verify_roster_call_abi.py` 从九份来源锁重建十六个完整原函数，验证保存证据和代码 SHA-256，遍历 2,032 个带堆叠状态的控制流程节点。它核对可确定偏移的直接堆叠访问；`FDCAB6` 的已保存局部指针循环被保守记为未知范围，`FDCAAA/FDCAB6` 列入 `dynamic_stack_accesses_pending`，两个变更步长/起点的反例被拒绝。不能从传给辅助函数的容量 16 推断其返回值一定小于等于 16。外部尾跳目标单独列为 `external_tail_abi_pending`；间接辅助函数、实际调用端、私有寄存器约定及运行期异常表没有因此被证明。离队 605F28 的 `JMP [R8+0x480]` 只按确切来源字节和已恢复 RSP 记录为 `indirect_tail_abi_pending`，不标为 ABI 已通过；改动目标偏移、破坏栈恢复及其他函数出现间接尾跳的三个反例均拒绝。这些仍是生产发布前置条件。

## 同一 owner 内的嵌套

`ep_roster_owner_call` 在锁内使用当前 revision，普通排队原生调用不会因为先查询 revision 的竞态而被丢弃。顶层调用持有真实 owner 引用和排他锁；同线程、同一 owner 的原生嵌套继承该范围，最多 32 层，不再次取得锁。内部搬移、注册表的 tag 73 关联查询和离队 getter 均直接使用同组主体，继承外层保护。注册表入口保守视为写入；关联查询返回 entity ID，不是 network index。

entity→network index getter 与关联 entity 查询标为只读，其余入口保守标为可能写入。只要顶层或任何嵌套调用可能写入，成功的最外层调用就增加一次 revision。纯读取不增加；嵌套异常不能被外层正常返回掩盖，首个故障原因保留，后续调用拒绝。写入 revision 到 UINT64_MAX 时不能回绕。

只有上述原生调用允许同 owner 嵌套。跨 owner、不同 Mod 的嵌套，以及在普通 snapshot/mutate 作用域中发起原生调用仍被拒绝。snapshot、身份更新、close 等管理接口不开放重入。`ep_roster_owner_in_scope` 只查询线程局部状态；组提交用它在外部排空开始前拒绝任何在途 owner 作用域中的切换请求。

原生调用不会自动改写身份票据。名册变化后，如果票据尚未与权威身份同步，读取器继续返回 pending/身份不匹配；不能把原生入队当作账号身份确认。

## 提交与失败契约

带 owner 的组仍要求外部 guard，但顺序更严格：

1. `begin` 在未持有 owner 锁时停止并排空相关外部执行，取得稳定 lease。它只负责排空和寿命，不能提前修改受管数据；否则可能与尚在运行的旧调用竞争。
2. 取得 owner 后，`validate` 才准备并验证完整容量事务。验证和共同开关更新都在同一范围内；`validate` 的结构化异常由继承的内层边界捕获，外层保护仍然保留。
3. `end(committed)` 在该外层范围内完成恢复或失败清理。返回后才释放 owner，读者无法在准备或清理中间读取数据。如果在进入 owner 前就发现 owner 已关闭/不可用，`validate` 不运行；此时锁外的 `end(...,0)` 只能释放 `begin` 的排空 lease，没有受管数据可回滚。
4. 已激活后 `end` 意外异常会隔离 owner，并保留 ACTIVE 状态；不得伪装成未启用再取消。验证异常时保持旧开关并隔离 owner。隔离不是数据回滚，真实恢复仍由生产事务实现。

`EpRosterCallPolicy.failure` 是必填的 C ABI 回调。它接收入口编号、owner 错误与返回 frame，由调用方按照真实入口契约填写失败返回值；框架不为所有入口发明一个通用成功/失败 sentinel。测试中的 `0xEE000000+kind` 和浮点 -99.5 仅属于合成目标，不能用于游戏。

回调不得抛 C++ 异常、longjmp、等待反向锁或重入 owner 管理接口。生产 guard 的 begin/end 仍不得失败；SEH 是故障隔离边界，不是异常后的正常运行承诺。context、失败函数与被转交的代码必须覆盖已发布 hook 的全部寿命；关闭 owner 后旧 hook 只执行失败策略，不能释放其策略 context，也不能回退到四槽函数。

## 验证与复现

`tests/roster_call_dll.cpp` 编译真实 owner、调用桥和组实现。实际生成器、代码封存、函数表和 SDK/MinHook 链均保留；只把候选主体的第一个指令替换为到自有测试函数的无栈尾跳。Windows 宿主不执行游戏函数体。原候选主体继续由既有 Unicorn 验证覆盖。

本轮完整构建的 48 个新进程场景、12,440 次检查全部通过：正常并发切换、嵌套故障、嵌套深度上限、关闭排空、验证异常、结束异常、revision 耗尽、owner 已不可用，离队尾调用期间的关闭、提交等待及嵌套删除异常，以及十六个发布位置各自的 SDK 调用前/后失败。检查包括：

- 编译器按六参数原型发出的调用，包含高 32 位非零的参数和返回值；XMM 参数、浮点返回，以及完整易失返回寄存器。
- 独立汇编调用端设置全部 8 个非易失 GPR 与 XMM6–15，再从实际硬件结果验证保存；非发送调用使用不可访问的原参数地址，验证无需复制额外参数。
- 两个静态桥的 76 个指令边界，以实际 DLL 的 PE 函数表执行 Windows `RtlVirtualUnwind`，核对返回栈、地址、非易失 GPR/XMM。测试夹具逐字节匹配实际加载的桥接代码。
- 原生旧调用占用 owner 时提交必须等待；提交的验证和 end 阶段，实际 snapshot 仍被阻挡。事件顺序由生产注册表的引用计数确认，没有替代实现的测试锁。
- 同 owner 嵌套只提交一个 revision；跨 owner/Mod 拒绝；受保护调用内不得启动切换；故障隔离、关闭后失败策略、旧 handle 不串到新 owner，以及 DLL 释放后的固定代码寿命。

复现沿用 [引擎完整构建命令](engine/README.zh-CN.md#重建与证据)。总收据 `evidence/engine-roster-validation.json` 的 `roster_calls` 记录实际检查数量、48 个场景和边界；`roster-call-abi-validation.json` 保存原函数的直接堆叠证据。源文件、DLL/EXE 和 `.unwind.bin` 夹具指纹同时写入收据。

离队自有目标另有真实的无栈间接尾跳；测试确认尾跳目标仍持有 owner，旧/新路径内嵌套 getter 和两个删除入口只提交一个 revision。嵌套删除异常隔离 owner，关闭和提交等待尚未返回的尾调用。该合成四参数目标不能证明游戏通知目标的 ABI。现在第 16 个入口提供调用者范围：新增双阶段自有 dispatcher 在离队返回后才调用注册删除，测试中间间隙的快照/切换/关闭等待、同一次 revision、嵌套故障隔离，以及后来插入的原链路。故障测试刻意保留原 dispatcher 的后续非受管工作，证明隔离不等于自动中止或回滚。保存的完整游戏 dispatcher 没有被模拟执行，详见 [范围与来源](ENTITY_REMOVE_SCOPE.zh-CN.md)。
