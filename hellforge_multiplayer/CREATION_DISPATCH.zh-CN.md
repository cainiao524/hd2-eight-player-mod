## 80 次执行分别证明什么

每组在两个不同模拟代码基址执行，所有地址都属于 Unicorn 的模拟内存：

| 场景 | 次数 | 结果 |
|---|---:|---|
| 只接元件 239，已有 0–8 项，使用八槽 C++ 插入 | 18 | 第 1–8 项插入并返回；第九项进入容量拒绝出口 |
| 只接元件 239，已有 0–4 项，使用保存的四槽原代码 | 10 | 第 1–4 项正常，第五项触发原来的空地址写入断言 |
| 使用九元件参考顺序，元件 33 执行原代码 | 10 | 已有 0–3 项可经过选定路径；已有四项时在 33 的 `51AC8E` 拒绝，尚未执行 239 插入 |
| 仅在模拟内存把 33 的容量常数改成 8 | 2 | 第五项造成相邻数组覆盖，作为必须被识别的反例 |
| 资源类型为 `FFFFFFFF`，已有四项，八槽名册 | 2 | 名册成为五项，但资源序号仍为 `7FFF`；原分派入口仍返回 |
| 九元件顺序，33 与 239 第一回调均使用 C++ 八槽代码，已有 0–8 项 | 18 | 第 1–8 项经过两个插入器；第九项在 33 拒绝，旧数组和新区域边界保持不变；外层先行写入仍存在 |
| 上一组加入 33 第二/第三回调及属性/重置 C++ 映像，已有 0–8 项 | 18 | 第 1–8 项生成四个属性描述符、传给资源契约替身并完成 primary 和全局重置；第九项仍在第一阶段拒绝 |
| 初始化整合模式，已有七项、资源类型为 FFFFFFFF | 2 | 第八项属性/重置仍执行，名册与元件33均增至八项，但资源序号仍为 7FFF |

测试检查真实资源记录、句柄表、资源搜索游标、metadata 默认指针、owner8 序号表/计数、三张回调表的顺序，以及返回栈、非易失寄存器与 XMM6–15。外部替身会破坏易失寄存器和调用者影子空间，防止测试依赖偶然保留的值。原指令的写入必须落在明确列出的模拟数据区或栈内。

`FFFFFFFF` 场景是保存代码明确跳过资源提供者的分支，不是替身自行声称一次创建失败。`7FFF` 是该分支写入的无效序号；不能把“入口返回、名册增加”解释为角色建立成功。

## 必须修复的两个原子性缺口

**第一个缺口发生在元件拒绝之前。** `FDC140` 先把句柄写入 `context+F1AEB0` 的哈希表、写好资源记录、前移 `context+F32F14` 搜索游标，并填充 metadata 的两个默认指针，然后才调用第一张元件表。因此，八槽名册的第九项拒绝虽然保护了名册自身，外层资源记录和句柄表已经变化；配对的尾回调也还没有执行。

拒绝出口不能直接返回一个布尔值就宣称整次创建没有副作用。必须在外层写入前完成各资源的共同接纳检查，或实现覆盖全部已发生副作用的补偿及清理。现有 [ROSTER_CALLS.zh-CN.md](ROSTER_CALLS.zh-CN.md) 的 owner/quarantine 机制不能自动等同于这一创建事务。

**第二个缺口发生在名册插入之后。** 第一张回调表先加入名册，后续才决定实际资源序号。资源类型无效分支保留 `record+10 = 7FFF`，已经加入的名册仍存在，后续第三张回调表也会执行。完成条件必须同时核对资源结果与记录生命周期，不能只检查名册计数。

## 元件 33 不能只改容量常数

`S33 = component owner + 3CA0`。旧指针数组从 `S33+70` 开始，每项 8 bytes；第五项写到 `S33+90`，覆盖字节状态区。旧 primary 从 `S33+98` 开始，每项 `50` bytes；第五项从 `S33+1D8` 开始，覆盖 secondary 区。两个反例均实际执行原写入并核对覆盖后的字节。

负对照只修改了模拟内存中的比较常数。没有把这个改法写成候选映像、安装补丁或容量提供者。现已实现 [元件 33 八个映像](NATIVE_COMPONENT33.zh-CN.md)，包含四个核心、两个分类和两个初始化函数。18 次核心与 20 次初始化整合使用独立八槽数组，原版负对照保留。下一步须迁移其他直接 owner 和 registry 别名访问，补齐分配失败补偿、旧数据迁移及生产所有权。

## 明确保留的替身与未完成范围

资源/世界接口、变换处理、临时列表初始化、属性临时分配与清零 helper，以及除第一张表的 33/239、第二/第三张表的 33 外的其他元件回调均为显式替身。新增 20 次初始化整合运行保存的 `51ADB0/51ADE0` 包装器与当前 C++ 属性/重置主体；合成输入转换为 56-byte payload 和四个描述符，后续第二阶段替身观察 count=4，资源替身接收对应数组及 count=4。前 60 次场景保留原本零描述符对照。真正单位资源分配仍未执行。

此创建执行器的元件 33 仍只走 total=dense=prefix 的密集插入，没有触发其搬移路径；搬移、普通插入、移除、分类及分类后初始化在独立验证中执行。收据分别记录 `component33_core_integration_runs=18` 与 `component33_initialization_integration_runs=20`，不能将两类重复累计为新增生产入口。

这里直接配置模拟回调表，没有把生产 owner、SDK hook 链、排空及创建外层范围放进同一次执行。未验证的还有真实单位资源的 ABI、完整部分失败清理/重复回调、所有读写者、生产身份与内存所有权、接纳、控制、复制和八账户任务流程。`installable`、`runtime_verified`、`multiplayer_verified`、`public_release_allowed` 均保持 false。

## 离线复验

在仓库根目录，先按 [HANDOFF.zh-CN.md](HANDOFF.zh-CN.md) 运行固定上游的完整离线构建。已有对应自有测试 DLL 时，可单独执行：

```powershell
py -3.12 -B hellforge_multiplayer/tools/validate_creation_dispatch.py `
  --library hellforge_multiplayer/build/property_image_test.dll `
  --component33-library hellforge_multiplayer/build/component33_image_test.dll `
  --out work/creation-dispatch-validation.json
```

执行器只读取仓库保存的证据、自己的测试 DLL 与明确指定的输出文件。任何下一次游戏操作都需要新的明确授权；本文件不恢复历史 PID 或消耗已用完的单次授权。
