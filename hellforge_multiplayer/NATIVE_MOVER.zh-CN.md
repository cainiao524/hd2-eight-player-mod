# 四数组搬移器的原生生成与回溯

2026-10-25。固定游戏构建 25480438、HellForge SDK 13。`mod/src/ep_mover_image.*` 将 RVA `0x60C410` 的共用玩家记录搬移候选加入研究 Mod 的 C++ 生成、重定位与 READY 准备流程。插入和删除依赖这个共用写入入口；分类使用自身搬移路径及临时资源辅助函数。已完成独立映像、离线集成，并加入 [十二入口组](ROSTER_GROUP.zh-CN.md)；游戏内发布尚未执行。

## 数据与接口

`EpMoverAddresses` 输入游戏基址、代码地址、名册 S 地址、整个 B 存储地址和拒绝出口。原生调用约定为 RCX=S、EDX=目的 ordinal、R8D=来源 ordinal。

| 数组 | B 内偏移 | 每项大小 | 八项占用 |
|---|---:|---:|---:|
| descriptor 指针 | 0x000 | 0x08 | 0x040 |
| 主记录 | 0x040 | 0x70 | 0x380 |
| 辅助记录 | 0x3C0 | 0x38 | 0x1C0 |
| 网络属性 | 0x580 | 0x20 | 0x100 |

当来源与目的的低 DWORD 相等时，立即返回，不读取 S/B、不保存寄存器，也不写堆栈；即使相等值是 8 或 `0xFFFFFFFF`，仍保持原来的空操作。否则先检查两个 ordinal 小于 8 及 RCX 绑定，失败在任何数据读取或堆栈写入前跳到外部拒绝出口，R10D 给出原因 1/2/3。

成功路径依次搬动四组记录，然后恢复 S 作为哈希表基址，将来源实体的映射更新为目的 ordinal。记录位置改变，属性中的网络索引保持原值。它保留原哈希查找行为，**要求已有有效的来源实体映射**；不验证任意损坏的哈希表，也不代替名册所有者的寿命与写入排除契约。

纯生成接口 `ep_mover_image_build` 只处理数值，不解引用输入地址。它检查低 canonical 范围、对齐、B-0xE8 不下溢、包含全部元数据的已知区间互斥、三个外部拒绝跳转的 signed rel32 范围；失败清零输出。模板内六处重定位为两处 S、一处 B-0xE8、三处拒绝地址。

`ep_mover_code_prepare` 分配 612 bytes RW，按实际地址生成，再由会话所有者封为 RX、登记两条函数表记录，成功返回 READY；尚未发布，因此可以取消。失败清理、清理失败保留句柄供重试的规则与 getter 相同。初始化不调用该接口，不自动绑定或安装 hook。

## 分段回溯的处理

`native-mover.lock.json` 固定原始 430 bytes、证据和既有测试指纹。保存捕获中三条函数表记录及相应 UNWIND_INFO 共 92 bytes，经离线逐字节重放；其中两段链到主段，没有语言层 handler。保存 PE 头指向的异常目录未完整捕获，运行期有效异常表仍未确认。

旧 545-byte Python 搬移候选包含独立的检查和恢复 S 跳板，不能直接复用原函数的条件保存回溯表。新映像使用一个无栈前段和一个统一保存的主体：

| 内容 | 大小/位置 |
|---|---|
| 无栈检查、拒绝分支与相等返回 | 0～95，96 bytes |
| 主体统一 prologue | 从 96 开始，22 bytes |
| 全部代码 | 558 bytes |
| 无栈前段 UNWIND_INFO | 560，4 bytes |
| 主体 UNWIND_INFO | 564，24 bytes |
| 两条 RUNTIME_FUNCTION | 588，24 bytes |
| 完整映像 | 612 bytes |

主体将原来的 RBP/RSI/RDI 条件保存提前到公共入口；原位置换为 NOP，原恢复指令保留。RBX 先存到入口 RSP+0x20，再 PUSH R14；回溯资料沿用保存证据中的顺序原则：在 push 完成处使 RBX 的保存有效，先从最终 RSP+0x28 恢复 RBX，再撤销 R14 的 push。这样覆盖第一条保存与 push 之间的中间状态。RBP/RSI/RDI 分别位于最终 RSP+0x10/+0x18/+0x20。

主体的 26 处数组偏移和 4 条内部分支另由独立操作数解码检查。恢复 S 的 MOV 嵌入主体；没有带着已保存栈帧离开主体范围的内部跳板。模板生成默认只核对，显式 `--write` 才更新；Mod 运行时不依赖 Python。

## 已验证的范围

收据为 `evidence/native-mover-validation.json`，总引擎收据交叉固定其指纹。

| 检查 | 结果 |
|---|---|
| 既有功能用例 | 8 个测试、100 次执行：84 次候选、16 次原始四槽对照 |
| 搬移语义 | 全部 64 种来源/目的组合；逐页值与有序写入地址流一致 |
| 边界 | 高位参数、第二组地址、无映射数据下相等返回、写入前拒绝、三个 rel32 的交集端点 |
| C++/Python 完整映像 | 10 组有效输入一致、51 组无效输入拒绝且输出全零 |
| 接口与来源 | 2 项空输入/输出检查、1 项原语言处理器拒绝检查 |
| Windows 回溯 | 8,231 个逐指令上下文通过；1 份人为破坏 RBX 偏移的元数据被负面对照拒绝 |
| 实际准备/释放 | 25 项检查通过，包括两段函数表查找、RX、保护失败、释放失败重试 |

候选代码只在 Unicorn 的合成地址空间执行。Windows 自有测试进程只登记映像并执行回溯 API，没有直接执行游戏函数体。人为破坏的对照不代表原游戏函数存在该错误。

插入/删除/重新加入的三份存储映像和八端同步前的 64 次插入，现都绑定 C++ 实际生成的搬移代码。[四个插入入口](NATIVE_INSERT.zh-CN.md) 也已改用 C++ 输出，并直接检查完整 612-byte 搬移范围。[两个移除入口](NATIVE_REMOVE.zh-CN.md) 也已进入 C++ 生成及准备流程，并直接检查完整搬移范围；[两个分类入口](NATIVE_CLASSIFY.zh-CN.md) 使用各自代码和临时资源契约，另有分类重排的读取连接验证。旧 bundle 的代码长度不能作为生产完整映像的分配或共同发布依据。

完整重建使用 [引擎离线构建入口](engine/README.zh-CN.md#重建与证据)，会自动先构建测试 DLL，再运行搬移器及后续存储/同步验证。仅重跑搬移器：
