# 八端原生属性数据转发验证

2026-10-25。目标仍是八名真人完成同一任务。本次验证把既有原生属性候选、HellForge 后端和新的名册读取器连接起来；没有安装 Mod、连接 Steam 或运行游戏客户端。

## 实际执行的链路

1. 在八个独立 Unicorn 内存空间内各执行八次既有 x64 插入候选，共 64 次。每端名册顺序不同，同一成员在各端的本地 entity ID 也不同。
2. 每端为自己的成员执行保存代码对应的属性发送候选（原入口 `0x60C640`），并执行原始本地索引查询函数 `0x134F190`。索引查询使用合成的 confirmed-peer 表；分配器由显式测试回调提供 32 字节空间。
3. 从发送函数实际生成的八个属性描述符读取其值，逐项核对 hash、类型和地址，再按原顺序拼成 32 字节属性块。**拼接由测试完成，未执行游戏完整封包器。**
4. 这些属性块经过固定上游源码的 `PartyService` 与 `Frame` 编解码，从八个端点各发给其余七端，共 56 次。底层传输是内存队列；检查每份内容和发送端点、无重复、无回显、未接纳的第九端收不到数据。
5. 每个接收端用本地实体映射调用接收候选（原入口 `0x60C890`），让实际 x64 指令将七份远端属性写入各自存储。**实体映射和函数调用由测试桥接，未执行游戏网络实体分派。**本端自己的属性此前已由发送候选写入。
6. 在每端对八名成员执行 [实体到网络索引 getter](NATIVE_GETTER.zh-CN.md) 的 C++ 生成代码，共 64 次；按本端实体 ID 查询，核对网络索引、参数/栈/非易失寄存器保持，以及没有栈外写入。
7. 将八份最终存储交给 `ep_native_roster_snapshot`，再绑定到实际补丁后的 loader，调用 `EpRosterRead`、`PollPlayers` 和 `ActPlayerCount`。检查所有 peer、本地 entity、网络索引、代次和本地玩家标记；每端人数为 8，重复读取不重复报告生成。

发送者网络索引使用 `(3 × 成员序号 + 2) % 8`。各端 ordinal 排列另外改变，HellForge endpoint ID 另由服务分配，三者没有互相替代。初始未收到远端属性时，读取器拒绝不完整身份对应；完整属性到达后才接受八人名册。额外破坏一个索引后同样拒绝，不产生新生成事件。

## 结果与证据

两份属性映像现由 Mod 的 C++ [进程内生成器](PROPERTY_IMAGES.zh-CN.md) 输出。每次先与独立 Python 参考逐字节比对，再将 C++ 产生的代码交给 Unicorn。入口显式要求 `--property-library` 指向本次编译的 `build/property_image_test.dll`；完整引擎构建会自动传入，不加载安装目录的 DLL。仍未在宿主上原生调用游戏候选。

发送端和接收端现已分别使用 [Windows unwind 适配变体](NATIVE_UNWIND.zh-CN.md)：规范化 prologue、修正各自两个拒绝跳转并生成独立回溯资料。接收端把条件保存移至入口，让 sentinel 等早退路径也具备完整的非易失寄存器保存。八端测试执行两份新代码；元数据另由真实 Windows API 在自有进程验证。生成映像和函数表不代表已经安装生产 hook 或验证原异常处理器。

| 范围 | 结果 |
|---|---|
| 原生插入 | 64 次成功 |
| 原生属性发送及本地索引查询 | 各 8 次成功 |
| 后端转发及原生属性接收 | 各 56 次成功 |
| 接收后实体 ID 到网络索引查询 | 64 次成功；与发送端内部的本地索引函数分开验证 |
| 后端集成模式 | 264 次检查通过；含原有 132 次、3 次输入检查、129 次属性转发检查 |
| 八份接收名册到实际 loader | 1,678 次断言通过，包含逐次复制与租约检查，并非独立场景数 |
| 原有验证 | 适配器 26、基础后端 132、引擎消费者 100、存储连接 589 次检查/断言保持通过 |

收据为 `evidence/engine-roster-validation.json` 的 `native_property_sync`。`artifacts` 固定输入、转发结果、接收执行记录、八份前后存储映像和测试程序的 SHA-256。源码固定在 `test_source_sha256` 与 `native-storage.lock.json`；原有保存证据没有改写。

复现仍运行 [引擎离线构建入口](engine/README.zh-CN.md#重建与证据)。它会按顺序运行 `native_roster_sync.py produce`、带原生属性输入参数的后端测试、`native_roster_sync.py consume` 和 `native_roster_sync_test.exe`。新增依赖为既有后端测试所用的 .NET 10 SDK；Python/Unicorn/Capstone 版本与原存储测试相同。产物保存在被忽略的 `build/`。

## 不能据此宣称的结果

本次证明固定候选产生的八组属性值可以经过实际 HellForge 后端保持内容，并被接收候选写到不同布局的正确记录中。它没有证明游戏真实发送/接收会调用这些候选，也没有证明游戏完整包格式、实体分派、网络丢包/重排行为或 Steam 传输。

confirmed-peer 表、peer、lifecycle、实体描述符、身份代次票据和接纳结果仍由测试提供。原生发送函数此时生成的 avatar network ID 为 `0x7FFF`（尚无 avatar），不能把 loader 的合成生成事件当作真实角色创建。角色创建后的属性更新、死亡/增援及任务状态复制仍需继续接入。

真实 owner 绑定仍有一个明确要求：Bridge 的 retain/release 只能防止对象释放，不能阻止其他原生写入。必须先接入全部相关写入路径，建立读写互斥与撤销顺序，才能兑现读取器的租约契约。此测试没有增加虚假的“所有者已绑定”标记，也没有自动启用容量修改。
