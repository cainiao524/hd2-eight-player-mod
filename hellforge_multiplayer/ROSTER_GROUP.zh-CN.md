# 十四个名册入口共同发布与切换

2026-10-26，固定 HellForge SDK 13、游戏 build 25480438。`ep_roster_gate.*` 和 `ep_roster_group.*` 将已经移植的名册读写入口放到同一个开关、同一 S/B 绑定及同一个准备/发布事务中。研究 Mod 初始化没有调用它；真实游戏暂停、完整容量准备和激活后回滚仍未实现。

## 覆盖范围与代码布局

各入口从 1 开始编号，绑定数组使用编号减一。原 `prepare` 接口的最前方是 32-byte 转发开关：仅在共享值为 1 时进入新主体，否则从 SDK 保留的下一跳变量转发。该直接开关不改整数参数、XMM、非易失寄存器和 RSP；只使用 RAX 和标志。新增 `prepare_owned` 在同样的 32-byte 区域用 R10/R11 转入静态 ABI 桥，先取得 owner 再选择路由，详见 [受管调用](ROSTER_CALLS.zh-CN.md)。该区别不改变下面的主体地址、映像长度或回溯段数。

| 编号 | 入口 | 原 RVA | 完整映像 bytes | 回溯段数 |
|---:|---|---|---:|---:|
| 1 | 属性发送 | 0x60C640 | 756 | 2 |
| 2 | 属性接收 | 0x60C890 | 484 | 2 |
| 3 | entity→network index | 0x606AD0 | 436 | 2 |
| 4 | 共用搬移 | 0x60C410 | 660 | 3 |
| 5 | dense legacy 插入 | 0x60CA80 | 688 | 3 |
| 6 | append legacy 插入 | 0x60CBA0 | 588 | 3 |
| 7 | append registered 插入 | 0x540850 | 592 | 3 |
| 8 | dense registered 插入 | 0x540920 | 684 | 3 |
| 9 | legacy 移除 | 0x60CEA0 | 824 | 3 |
| 10 | registered 移除 | 0x540A40 | 808 | 3 |
| 11 | enter 分类 | 0x60CF50 | 2,344 | 3 |
| 12 | leave 分类 | 0x60D300 | 2,816 | 3 |
| 13 | registry update | 0xB54E00 | 1,884 | 5 |
| 14 | association entity | 0x606520 | 536 | 4 |

候选按最终地址 base+32 生成，函数表及链式父记录中的三个 RVA 均加 32。已有入口保持原布局；注册表使用五段、关联查询使用四段。`ep_session_code_seal_table` 接受 1–5 段，每段使用独立回溯资料并拒绝重复引用；链式父项必须逐字节匹配同一表中较早的记录。重叠代码、错序、越界、循环/向后续记录引用、语言 handler 和不支持的操作仍拒绝。

`prepare` 先保留全部十四份代码，再生成和封存。插入/移除中的搬移调用统一绑定第 4 幅映像的**主体地址 base+32**，不绑定旧函数或另一个独立开关。tag 73 关联查询绑定第 14 幅映像的主体地址 base+32，额外检查完整 488-byte 主体范围。外部对原搬移函数的调用仍经过第 4 个开关。已选择新路径的内部调用不能中途重新选择旧路径。

每个生成器检查整个 S=0x428、B=0x680、原十四个函数、已知全局和辅助函数，以及本映像、控制字、下一跳和拒绝出口。插入/移除另外检查完整 612-byte 搬移主体范围。组再检查所有代码的完整已提交页面（含映像尾端空白）、所有下一跳槽位与拒绝出口，防止封为 RX 的页面内仍放有玩家存储。

## 生命期与调用契约

使用 `EpRosterGroupBindings`、`EpRosterGroupInfo`，以及既有 `EpPropertyCommitGuard`。状态仍为 `EP_GROUP_*`。一次准备消耗 12 个共享代码槽；组最多 4 个，共享代码所有者仍只有 64 槽，其他使用者可能使准备更早失败。失败返回明确，不复用仍暴露的句柄或代码。

1. 在任何发布前，生产调用方必须核对运行中游戏映像、目标字节、ABI、有效异常表、拒绝路径和外部资源。保存来源锁及 SDK build 字符串不替代这些检查。
2. `prepare` 生成并登记全部代码，开关为 0；任一分配、生成、封存失败都清理未发布对象。清理失败保留组句柄，允许重试取消。
3. `publish` 顺序发布 12 个 hook。全过程保持旧路径；任一 SDK 调用前后报错都使组进入 FAILED。已尝试发布的代码和下一跳永久保留，取消只清理未暴露部分，不能当作从未挂钩。
4. 全部发布成功后才到 READY。`commit` 要求 `begin/validate/end`：停止并排空相关执行（含已选择旧路径的调用），准备及验证房间、Party、peer、名册、实体、复制和资源的完整容量状态。
5. 验证成功后一次原子交换将开关设为 1，再恢复执行；失败时保持 0，由 `end(...,0)` 撤销已准备数据。回调不得抛异常；end 不得失败。COMMITTING 期间拒绝重入、发布和取消。
6. ACTIVE 后拒绝取消，避免把八槽状态送回四槽函数。完整数据回滚和会话结束处理仍须另行实现；外部存储及拒绝处理器须至少保留整个会话。

三入口 `ep_property_group.*` 保留给已有独立验证及调用方；它不能和十四入口组分别激活来拼成一个事务。生产集成应使用十四入口组并落实整个 guard 契约。十四入口也只是已定位的名册入口，不能据此声称已覆盖全部游戏玩家消费者或全部容量。

## 验证来源与界限

`evidence/roster-gate-validation.json` 记录实际 C++ 生成的十四个开关分支、拒绝条件及 Windows 回溯。验证逐字节比对加开关前后的代码主体；含链式回溯的元数据按 +32 重新定位后另由 Windows 核对。验证还重用对应功能测试实际捕获的完整不同上下文，再将所有 PC 加 32；保存的负对照保留其原有含义，没有将人为破坏当成原游戏缺陷。

`evidence/engine-roster-validation.json` 的 `roster_group` 记录 29 个自有进程场景：正常生命期和每个发布位置的 SDK 调用前/后故障。测试实际调用 HellForge HookAdd/ApiHookEx/MinHook，验证十四个下一跳、全部准备位置的封存/清理失败、多段回溯错误拒绝及注册表内部关联目标绑定、共享资源和页面范围、guard 重入拒绝、旧调用排空、句柄/槽位耗尽，以及 DLL 释放后仍可调用。

宿主只执行合成函数：实际生成器先完成后，用单条无栈间接跳转把主体入口指向编译器产生的测试 leaf 函数；只在该入口偏移 0 上经过原 prologue 资料。原候选主体不在 Windows 宿主执行，完整主体功能来自此前 Unicorn 验证；新入口的主体字节与那些验证映像逐字节一致。并发测试的锁由测试线程共同遵守，尚无游戏线程的真实写入排除证明。

重建入口见 [引擎说明](engine/README.zh-CN.md#重建与证据)，总脚本会自动执行所有新增检查。本次实际通过 84 组入口分支、122 组非法配置拒绝及 45,598 个 Windows 回溯上下文；29 个成组场景合计 10,965 次检查。原三入口组 355 次、会话代码所有者 383 次及八端属性链仍通过。检查数量包括每个调用阶段的断言，不是实际游戏玩家或独立玩法场景数。

## 下一步

新增 [存储所有者](ROSTER_OWNER.zh-CN.md) 已实现受管读写互斥、revision/票据提交、代次墓碑与关闭排空，并连接真实 loader 的离线消费者。[受管调用](ROSTER_CALLS.zh-CN.md) 进一步提供 `prepare_owned`：十四个旧/新入口共享 owner，允许同 owner 原生嵌套，提交准备和清理也在保护内。其 guard 的 `begin` 只排空，不得先写数据；完整契约见该文档。该显式接口未接入生产，不能据此声称所有游戏写入已受保护。继续核对外部辅助函数/实际调用 ABI、其余读写者和拒绝契约，落实权威票据、生产排空、调用者 flag/通知、临时分配失败、完整容量与回滚，以及角色、复制和八账号任务验收。

保持 `installable=false`、`runtime_verified=false`、`multiplayer_verified=false`。没有新增游戏访问授权；本轮不启动、检查、读取、修改或安装游戏，旧一次性 64 KiB 采样预算不续期。
