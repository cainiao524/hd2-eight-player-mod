# 属性入口成组发布与共同切换

固定上游、SDK 13 与游戏 build 25480438 不变。`ep_property_gate.*` 为两份属性候选生成默认关闭的转发入口，`ep_property_group.*` 通过实际 HellForge SDK 成组发布并持有会话资源。研究 Mod 初始化不会调用这些接口。**这不是完整容量事务，也没有生产环境的暂停/排空提供者。**

## 代码与所有权

每份映像先放 32 bytes 入口，再放既有属性候选；候选的地址重定位按实际起点重新计算。入口读取同一个对齐的 32 位开关：值为 1 时进入新函数体，其余值跳往 SDK 保留的下一跳变量当前值。下一跳没有复制成快照，后续 hook 插入可继续更新它。

入口只改 RAX 和标志，不改变整数参数、向量寄存器、非易失寄存器或栈。它按固定目标的 Windows x64 调用约定设计；集成者仍需核对真实目标及调用契约，不能把这个入口用于任意隐式寄存器 ABI。RAX 的易失属性见 [Microsoft x64 calling convention](https://learn.microsoft.com/en-us/cpp/build/x64-calling-convention?view=msvc-170)。

| 映像 | 完整长度 | 候选起点 | 两条函数表偏移 | 候选回溯 / 入口回溯偏移 |
|---|---:|---:|---:|---:|
| 发送 | 756 bytes | 32 | 732 | 704 / 728 |
| 接收 | 484 bytes | 32 | 460 | 432 / 456 |

两条 RUNTIME_FUNCTION 分别描述无栈帧入口和原候选。`ep_session_code_seal_table` 只接受一条或两条，不接受任意数量；检查排序、范围、回溯区间及重复/重叠。旧 `seal` 保留单条行为。Windows 注册时传入真实条数，见 [RtlAddFunctionTable](https://learn.microsoft.com/en-us/windows/win32/api/winnt/nf-winnt-rtladdfunctiontable)。

最多 16 个组；句柄单调递增，不复用身份。组、共同开关、代码所有者和稳定下一跳变量在同一个 DLL 中，发布前由所有者将这个 DLL 固定到进程退出。组内两份代码句柄的控制权交给组，调用者只能查询，不能单独发布或释放；否则违反 API 所有权契约。

## 调用顺序与失败语义

1. **生产调用者的前置核对尚未实现。** 在任何发布前，必须确认当前映像、目标函数字节、真实调用契约、运行期有效异常表、拒绝出口和引用资源。SDK build 字符串及离线来源锁不能代替这些核对。当前无自动安装入口。
2. `prepare` 分配两幅映像，生成并封为 RX，登记各自两条函数表。共同开关保持 0。任一准备失败，清理尚未发布映像；清理失败保留组句柄，可重试取消。
3. `publish` 依次调用真实 SDK。整个发布过程开关保持 0；只有两次都成功才进入 READY。任一调用前或后返回失败，都保持旧路由。尝试发布的代码、函数表、下一跳变量和组开关永久保留；不能把失败解释为从未暴露。
4. `commit` 必须提供 `begin/validate/end`。`begin` 应停止并排空所有相关执行，包括已经选择旧路由的调用，并在租约保护下准备所有相关容量和数据；成功时返回非空租约。若 `begin` 返回失败，必须先自行撤销准备和解除暂停，此时不会调用 `end`。`validate` 必须检查完整的房间、Party、peer、名册、角色、复制及资源状态，不能只检查两幅属性映像。
5. 验证成功后以一次 `InterlockedExchange` 将共同开关置为 1，再调用 `end(..., committed=1)` 恢复执行。失败时开关仍为 0，`end(..., committed=0)` 必须先撤回已准备数据再恢复。回调不能抛异常；`end` 不得失败。整个回调期间组保持 COMMITTING，递归提交或取消被拒绝。原子交换的内存屏障语义见 [InterlockedExchange](https://learn.microsoft.com/en-us/windows/win32/api/winnt/nf-winnt-interlockedexchange)。
6. `cancel` 只允许激活前调用。未暴露对象可释放；已尝试发布的组变成 CANCELLED 并保留转发入口，直到进程结束。**激活后拒绝取消，不会把仍承载八人数据的执行切回四人路径。** 成功提交后的外部资源必须保留整个会话。

原子开关不能自行排空旧调用，也不能让多个数据结构自动一致。缺少真实 guard 时不能提交；当前测试 guard 是测试线程共同遵守的锁，不能声称游戏线程已经采用了它。完整激活失败恢复、激活后数据回滚、会话结束清理和其他容量消费者的协调仍待实现。接口返回 1 表示成功，与 SDK hook_ex 的 0 成功不同。

## 已执行的离线验证

总入口仍为 [build_engine_offline.py](engine/README.zh-CN.md#重建与证据)，结果由两份收据记录：

- `evidence/property-gate-validation.json`：实际生产 C++ 入口的 12 组分支测试（两函数、三个开关值、两次下一跳值），核对参数、栈指针、向量和非易失寄存器；12 组错误对齐/重叠必须拒绝并清空输出。把原有 1,308 + 1,313 个上下文移到真实入口后，由 Windows 对两条函数表进行回溯，全部通过；原有 3 + 7 次负面对照错误仍被复现。
- `evidence/engine-roster-validation.json` 的 `property_group`：258 次检查。直接使用补丁后实际 HellForge HookAdd/ApiHookEx/MinHook，覆盖第一/第二次发布之前或之后报错、发布中取消拒绝、共同切换、缺失/失败 guard、回调期间重入拒绝、协作锁等待旧调用退出、16 组耗尽、旧句柄拒绝、后续 hook 更新下一跳，以及 FreeLibrary 后模块和链仍有效。另有十组无效双条回溯表被拒绝，并在入口不同指令位置直接验证 Windows 回溯。

成组测试 DLL 先用真正生成器校验和生成，然后仅将候选函数体替换成测试算术，保留对应入口保存/恢复约定。Windows 宿主只调用这些合成函数；真实游戏函数体只在原有模拟器中执行。另一份入口验证 DLL 使用未替换的生产生成器；Windows 在不可执行数据映像上读取其回溯资料。两种证据用途不同，不能混为游戏执行。

这轮只处理工作区源码、已有捕获及自有测试进程。旧 v2 一次采样已经消费，64 KiB 预算不续期；没有新的游戏安装、启动、检查、读取或写入。
