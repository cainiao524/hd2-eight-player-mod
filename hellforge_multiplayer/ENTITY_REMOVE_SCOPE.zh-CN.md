# 实体删除外层范围：HellForge 第 16 个入口

2026-10-26。固定 HellForge SDK 13、游戏 build 25480438。这次实现把原实体删除 dispatcher `FDC820` 的整次调用纳入可选的名册所有者，覆盖离队预清理返回后、真正名册删除开始前的间隙。旧/新模式都保留 SDK 当前下一跳。实现与自有进程验证不等于完整游戏离队事务通过；研究 Mod 初始化仍未调用它。

## 为什么需要外层入口

原第 15 个入口 `605950` 是移除前清理。只保护它会在返回时释放 owner，后续注册删除 `540A40` 尚未执行。已有保存证据显示，`FDC820` 从两张不同回调表分别派发它们：

| 阶段 | 表读取位置 | 间接调用位置 | 原 context 相对表基底 | component 239 回调 |
|---|---|---|---|---|
| 移除前 | FDC943 | FDC953 | F0DFB0 | 540B20 → 605950 |
| 真正移除 | FDCC53 | FDCC63 | F0E9D0 | 540A40 |

注册初始化器使用的 component owner 是原 context+0x40，因此对应注册表基底是 F0DF70 / F0E990。不能把两种基底混用，也不能把 component 239 当成名册位置或网络索引。

[来源锁](native-entity-remove.lock.json) 保存完整 1,503-byte 函数、SHA-256、两次调用的位置和注册证据引用。[来源与 ABI 检查器](tools/verify_roster_call_abi.py) 核对旧证据的七个连续函数片段、表基底差和调用位置。原字节 SHA-256 为 `8ef7ad9fbf59756023045f94c796bfb96a2f43876d8c64052c0d306a8b5c6094`。来源仍是既有固定捕捉，不是新游戏读取。

## 实现与行为

- `EP_ROSTER_ENTITY_REMOVE=16`，原 RVA `FDC820`。既有十五入口的编号及内部 helper 绑定不变。
- 组先配置全部十六份代码，再发布；未全部发布成功不能激活。四个组各占十六个共享代码槽，正好用完 64 槽；其他使用者占用时可以更早返回配置失败。
- 普通组的第 16 幅映像只有 80 bytes：32-byte 开关、16-byte 无栈转发段、8-byte 叶回溯资料和 24-byte 函数表。两种开关路径都读取 SDK 下一跳变量；它不包含原 dispatcher 的重定位副本。
- 受管组先取得 owner，再解析当前 SDK 下一跳，始终调用原链路。候选主体不替换 dispatcher；后插入的 SDK hook 仍在链中。
- 原调用未返回时，同 owner 嵌套入口继承其范围。预清理返回后，外层范围继续存在；后续移除完成并返回以后才释放。所有可能写入的嵌套只在最外层成功时增加一次 revision。
- `FDC820` 是通用实体删除入口，目前没有按玩家类型过滤。其余实体回调、锁顺序、并发及性能影响都属于生产前置条件，不能由玩家夹具推断。

## 验证实际覆盖了什么

实际 HellForge/MinHook、owner、桥接、代码封存和下一跳链在自有 Windows 测试进程中运行。游戏函数体没有在宿主执行；原完整 `FDC820` 也没有在 Unicorn 中执行。两阶段自有 dispatcher 是根据保存调用顺序构造的夹具，它不替代所有原实体管理分支。

`roster_call_test.c` 的五个新增模式：

| 模式 | 验证点 |
|---|---|
| scopecommit | 预清理已返回、移除尚未执行时，切换仍等待；原调用结束后才准备与启用新路径 |
| scopeclose | 同一间隙内关闭等待；已进入的外层调用仍可完成嵌套移除，排队调用被拒绝 |
| scopesnapshot | 快照等待，底层读取回调在间隙中没有运行 |
| scopefault | 预清理异常隔离 owner，后续受管删除和外层返回失败；原 dispatcher 的模拟非受管后续工作仍执行，明确暴露“不自动中止、不回滚” |
| scopechain | 后插入的 SDK 下一跳仍在 owner 范围中执行；旧/新模式均保留原 dispatcher |

所有正常模式还检查旧/新阶段的顺序、仅增加一次 revision，以及第 16 个候选替身绝不执行。普通组保留真实无栈转发字节，另检查动态下一跳和 Windows 叶回溯。分支模拟遍历三个开关值及两个不同下一跳，共六种情况。

总数见 [引擎验证收据](evidence/engine-roster-validation.json)、[开关收据](evidence/roster-gate-validation.json) 和 [ABI 来源收据](evidence/roster-call-abi-validation.json)：33 个成组场景、48 个受管调用场景；十六个发布位置的 SDK 前/后失败均覆盖。测试为数值 S/B/reject 区间预留不可访问地址空间，避免测试代码偶然落入这些合成地址而导致配置随机失败；没有增加真实游戏读取。

## 仍未证明的条件

`FDCA93` 调用一个外部函数，并传入容量 16 和指向栈内 128-byte 缓冲区的指针。原代码用返回 EAX 决定后续遍历次数；`FDCAAA` 读取当前项，`FDCAB6` 将指针推进 8 bytes。现有证据不能证明回调返回值不超过 16。

ABI 检查把该指针的范围保守地扩展为未知，而不是假设它永不越界。两个位置记入 `dynamic_stack_accesses_pending`；改变起点或步长的反例被拒绝。当前桥接对第 16 个入口不复制额外堆叠参数，但这不证明间接辅助函数或动态缓冲区契约完整。全组 2,032 个控制流程状态通过的是这个带明确未决项的检查。

另外仍需证明：

1. `605F28` 间接尾调用的真实目标、私有参数与返回契约；原 dispatcher 的其他回调和整体执行。
2. 所有相关实体类型及其他读写路径的锁顺序、重入、线程退出、实际调用端与有效运行期异常表。
3. 生产失败处理和外部副作用恢复。owner 隔离不能自动撤销原操作，也不能阻止未受管的原 dispatcher 继续运行。
4. 权威身份、存储寿命、生产排空、全容量事务、人数资源 5～8、角色创建/控制、复制、死亡增援、重连/迁移及八个独立账号完成同一任务。

`installable=false`、`runtime_verified=false`、`multiplayer_verified=false`。旧 PID 的一次性 64 KiB 采样已消耗，本轮授权只涉及项目源码和交接，不延续游戏访问。
